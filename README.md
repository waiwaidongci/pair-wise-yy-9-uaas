# 古法蓝晒 · 曝光批次与冲洗联审台

底片整理室扩成的「曝光批次 × 药液批次 × 冲洗联审」工作台。

```bash
npm start        # http://localhost:3040
npm test         # 19 项领域规则测试 + 9 项 HTTP 集成测试
```

数据保存在 `data/cyanotype-joint-review.json`（原子写：先写 `.tmp` 再 rename）。

## 业务规则

1. **药液批次互斥**：一个药液批次只能服务一个「未结束」曝光批次（复核中/待入盒/已入盒均算未结束，批次结束才释放药液）。冲突提交返回 `409 chemical_batch_conflict`，在任何写入前判定，不落库；服务端写操作全局串行，并发请求也不会双写。
2. **必填校验**：提交批次必须含玻璃板尺寸、曝光时长、冲洗水源、显影结果（密度 + 边缘情况），另有药液批次与操作员；缺项返回 `400 missing_fields`，不落库。
3. **显影结论失效**：
   - 冲洗水源变化，或曝光时长被补时（增大）→ 原显影结论立即失效；
   - 未入盒批次退回到「复核中」；
   - 已入盒批次保持盒位但标记「受影响」（统计中单独计数）。
4. **复晒与入盒门槛**：
   - 复晒必须由操作人之外的**另一人确认**，否则 `400 confirm_required`；
   - 原结论有效且密度合格、无边缘不均，或**末尾连续两次复晒**密度合格且无边缘不均，才可入盒，否则 `409 box_gate_failed`（中途一次不合格会打断连续计数）；
   - 复晒携带 `requestId`（或 `Idempotency-Key` 请求头），重复或并发请求直接沿用首次记录，不重复计数。
5. **一致性**：卡片与统计只来自同一个 `GET /api/state`（落库数据 + 服务端派生字段），筛选与搜索不改变统计，刷新后一致。

## 分层

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 规则 | `src/domain.js` | 纯函数领域模型，无 IO；所有规则、门槛、状态流转、统计与派生字段 |
| 存储 | `src/store.js` | JSON 文件读写、种子数据、原子落库 |
| 适配 | `server.js` | HTTP 路由、静态文件、写操作串行锁、错误码→HTTP 状态码映射 |
| 展示 | `public/index.html` `public/app.js` `public/styles.css` | 表单、批次卡片、统计条；只渲染服务端状态 |

## API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/state` | 全部批次（含派生字段）+ 统计 |
| POST | `/api/batches` | 提交曝光批次（201 / 400 缺项 / 409 药液冲突） |
| POST | `/api/batches/:id/review` | 冲洗联审（复核人 + 通过/退回） |
| PATCH | `/api/batches/:id/changes` | 变更药液/尺寸/时长/水源/显影结果；触发失效规则 |
| POST | `/api/batches/:id/resuns` | 复晒记录（另一人确认；`requestId` 幂等） |
| POST | `/api/batches/:id/box` | 入盒（门槛校验） |
| POST | `/api/batches/:id/end` | 结束批次并释放药液批次 |
